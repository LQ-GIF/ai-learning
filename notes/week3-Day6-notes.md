# W3 Day6 学习笔记：通用 API 调用函数封装
日期：2026/10/24

## 项目内容
- 把 W3 阶段五天重复出现的请求逻辑（状态码判断，重试，异常捕获，JSON 解析）抽取封装成通用函数 api_call()，放在 api_utils.py 里
- 用封装好的函数重写 GitHub 仓库查询脚本 github_api_v2.py
- 测试三种场景：正常获取成功、404 不重试、连接失败重试 3 次

## 为什么要封装
- 避免重复代码：5 个脚本复制粘贴同一套防御逻辑
- 方便统一修改：超时时间、重试次数改一处即可
- 健壮性一致：所有调用方共享同一套异常处理逻辑
- 业务代码更清爽：脚本只关注"调用谁、展示什么内容"

## api_call 函数设计思路
- 变化的部分做成参数：method / url / params / headers / timeout / json / max_retries
- 固定的部分写在函数内部：状态码判断、重试、异常捕获、JSON 解析
- 成功返回解析后的 JSON；失败统一返回 None，调用者先判断 None 再使用

## 异常处理最佳实践
- 4xx 客户端错误（400/401/403/404）：不重试，直接返回 None
- 5xx 服务器错误、Timeout、ConnectionError：自动重试
- 指数退避：重试间隔 1s ——> 2s ——> 4s，给服务器恢复时间
- 记录最后一次错误原因，重试次数耗尽后打印清晰提示
- 不吞异常：错误信息要打印出来，方便排查

## 指数退避原理
- 第一次重试等待 1 秒，第二次重试等待 2 秒，第三次重试等待 4 秒（2 的 n-1 次方）
- 服务器繁忙时密集重试只会添乱，递增等待更礼貌，更科学

## 文档字符串的作用
- 记录函数功能、每个参数的含义、返回值、异常策略
- 一段时间后回看不用读内部代码就知道怎么调用

## 封装前后对比
- github_api.py：自己写状态码判断、异常捕获、JSON 解析
- github_api_v2.py：一行 api_call() 完成全部防御逻辑，代码量明显减少

## 遇到的问题
- 现象：防御逻辑里连接失败应重试 3 次后提示报错，现实代码运行时只重试 1 次后就提示报错
- 原因：封装函数代码中把重试次数耗尽后的总结代码写在了 for 循环内，总结代码中有 return，导致 for 循环在第一遍循环结束时读取到了 return，自动跳出了循环
- 解决方法：将总结代码写在 for 循环代码块的外面

## 没搞懂的地方
基本逻辑都通了，但是将他们运用到真实的工程项目中独立写出来还是有不小的困难

## 今天的收获
了解了将不同项目中起到相同作用的代码可以封装成一个函数，既不影响代码功能的实现，又大大提高了代码的简洁性，维护、修改更加方便
